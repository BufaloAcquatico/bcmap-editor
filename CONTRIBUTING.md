# Contributing to BCMap Editor

This covers the developer workflow. For what the editor is and how to use
it, see [README.md](README.md).

## Prerequisites

- Node 22 (see `.node-version`; the package requires `>=20`)
- pnpm (`pnpm install` for dependencies)

## Build

```bash
# Install dependencies
pnpm install

# Build (typecheck + embed JS in map-editor.html + regenerate README tables)
npm run build

# Watch-compile only (does NOT re-embed: changes reach the page only
# through npm run build, then a hard refresh)
npm run dev
```

## Tuning motion

All animation durations live in `src/anim.ts` (`MOTION_MS` and
`MOTION_QUICK_MS`); canvas loops, CSS transitions, fades and tests all
derive from them, so retuning those two constants retunes everything.
Source edits only reach the page through a rebuild: run `npm run build`
after changing values, then hard-refresh (note: `npm run dev` compiles
without re-embedding, so it alone changes nothing visible). The live
tuning prints one `Motion durations: …` line to the devtools console on
every load — check there first if a retune seems to do nothing.

## Assets

```bash
# Download assets (drives from the shared catalog, with throttling)
# Existing files are skipped by default — do NOT use --force: most sprites
# are byte-identical across releases and re-downloading them is wasteful.
npm run download-assets -- --concurrency=1 --delay=500 --retries=6

# Verify every catalog asset is present and non-empty, without downloading
npm run download-assets -- --verify

# Options:
#   --force            re-download every asset (avoid; skip-existing default)
#   --concurrency=N    parallel requests (default 2)
#   --delay=MS         delay between requests (default 150)
#   --retries=N        retries per asset for 404s/timeouts (default 3)
#   --verify           check the local tree against the catalog, then exit
# HTTP 429 replies are handled separately: Retry-After is honored (5-30s
# backoff) and they do not consume the ordinary retry budget.
```

Sprites are pinned to a single Bondage Club release
(`BASE_URL` in `scripts/download-assets.ts`, currently **R134**). Only the
latest hosted release resolves on the asset server, so when the game
publishes a new version, bump that pin, regenerate the catalog (below),
and re-run the downloader with the throttled command above; finish with
`--verify`. If the host keeps rate-limiting, report it instead of forcing
the download.

The catalog in `src/catalog.ts` is generated from BC's
`Assets/MapData.js` and is the single source of truth: pickers, renderer,
importer, and this script all read it, so a game addition surfaces
everywhere. To update it after a game release, point the generator at a BC
checkout and commit the regenerated file:

```bash
npm run generate-catalog -- --source=/path/to/BondageClub/Assets/MapData.js
# BC_MAPDATA=/path/to/... also works; see the script for default paths.
```

Do not edit `src/catalog.ts` by hand. Connected-texture variants (R134
Kitchen/LivingRoom rows and fences) are listed in `src/constants.ts` and
consumed by the renderer, the preloader, and the downloader from that one
registry. If the asset server 404s brand-new files, they render as
color-fallback placeholders until the server publishes them. After regenerating the catalog or running `npm run build`, run
`npx prettier --write README.md src/catalog.ts` before committing: the
generated catalog and README tables are not Prettier-formatted on their own.

## Formatting

Prettier, 4-space indent:

```bash
npm run format
npm run format:check
```

## Tests

```bash
# Unit tests
npm test

# E2E tests (requires Playwright browsers)
npm run test:e2e

# E2E tests in Docker (no local browser install needed)
npm run test:e2e:docker

# Unit tests in Docker
npm run test:e2e:docker:unit
```

### Docker testing (recommended for Fedora/Linux)

Runs Playwright E2E tests without installing browsers locally.

**Requirements:** Docker and Docker Compose installed

```bash
# Build and run E2E tests
docker compose -f docker-compose.test.yml up --build --abort-on-container-exit test

# Or use npm script
npm run test:e2e:docker

# Run unit tests in Docker
npm run test:e2e:docker:unit
```

**Cleanup:** the test stack must be torn down after every run and stale artifacts removed; see `AGENTS.md` for the required commands.

**Files:**

- `Dockerfile.test` - Test image based on `mcr.microsoft.com/playwright:v1.64.0-jammy`
- `docker-compose.test.yml` - Compose file with volume mounts for fast iteration

## Technical notes

- TypeScript → compiled and embedded in `map-editor.html`
- Canvas 2D rendering with image caching
- Bootstrap 5 for UI (vendored, offline-safe)
- LZString for map-code compression
- Vitest (unit) + Playwright (E2E) for testing
- The Controls and Commands tables in the README are generated by
  `scripts/render-keybinds-doc.js` during `npm run build` — edit the
  keybind/command registries in `src/`, never the tables by hand.
